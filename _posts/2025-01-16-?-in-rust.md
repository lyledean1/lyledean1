Following up from my previous post on compiler development, I've been exploring how programming languages are built from the ground up. One fascinating aspect of this journey has been understanding how high-level language features are transformed into simpler constructs during compilation. Today, let's dive deep into one of Rust's most elegant features: the try operator (?).

## What is the Result type?

From the [Rust documentation for Result](https://doc.rust-lang.org/rust-by-example/error/result.html)
> Result is a richer version of the Option type that describes possible error instead of possible absence.
>
> That is, Result<T, E> could have one of two outcomes:
>
> - Ok(T): An element T was found
> - Err(E): An error was found with element E
> By convention, the expected outcome is Ok while the unexpected outcome is Err.

*Result is technically a Monad, but we will leave that explanation for another time*

Take this function, which can either return a f64 or an Error.

```rust
fn divide(x: f64, y: f64) -> Result<f64, String> {
    if y == 0.0 {
        Err("Division by zero!".to_string())
    } else {
        Ok(x / y)
    }
}
```

To handle this in Rust, you just need to match each possible return option from the result via 

```rust
match divide(10.0, 2.0) {
    Ok(result) => println!("Result: {}", result),
    Err(error) => println!("Error: {}", error),
}
```

Without the try operator, handling multiple fallible operations requires nested match statements or verbose error handling:

```rust
fn use_result() -> Result<f64, String> {
    match divide(20.0, 5.0) {
        Ok(first_result) => {
            match divide(4.0, 2.0) {
                Ok(second_result) => divide(first_result, second_result),
                Err(e) => Err(e)
            }
        },
        Err(e) => Err(e)
    }
}
```

## Enter the ? Operator 

An more idiomatic way of representing this in Rust is via the [try operator `?`](https://google.github.io/comprehensive-rust/error-handling/try.html). So instead of handling each match statement individually, you can include a `?` at the end of the function call which will either return the error or use the ok result

```rust
fn use_result() -> Result<f64, String> {
    divide(divide(20.0,5.0)?,divide(4.0,2.0)?)
}
```

Let's break down how this works:

1. First divide(20.0, 5.0)?:
    - If successful, returns 4.0
    - If an error occurs, immediately returns the error from use_result()
2. Second divide(4.0, 2.0)?:
    - If successful, returns 2.0
    - If an error occurs, immediately returns the error from use_result()
3. Finally, divide(4.0, 2.0) runs with the results from steps 1 and 2

## Desugaring 

Desugaring is a process in compilation where "syntactic sugar" - convenient syntax features that make code easier to write and read - gets transformed into more basic language constructs. It's essentially a way to simplify complex language features into simpler, more fundamental operations that the compiler can more easily process.

In this example, the Rust compiler takes the `?` operator and desugars that to match statements. We can do this by looking at the [HIR - "High Level Intermediate Representation" representation](https://rustc-dev-guide.rust-lang.org/hir.html) - running ` cargo rustc -- -Z unpretty=hir`

```rust
divide(
    // First ? operator desugars to:
    match #[lang = "branch"](divide(20.0, 5.0)) {
        #[lang = "Break"] { 0: residual } => 
            return #[lang = "from_residual"](residual),
        #[lang = "Continue"] { 0: val } => val,
    },
    // Second ? operator desugars to:
    match #[lang = "branch"](divide(4.0, 2.0)) {
        #[lang = "Break"] { 0: residual } => 
            return #[lang = "from_residual"](residual),
        #[lang = "Continue"] { 0: val } => val,
    }
)
```

So as you can see above, the `?` operator is now a `match` statement in the HIR IR. 
 
## Ok thats cool but what the hell is HIR? 

HIR is one of the intermediate representations of the source code that the compiler can more easily work with, specifically HIR is the "High Level Intermediate Representation" - one of the many IR (intermediate representations) after lowering the source code from AST, its followed by THIR (Typed High Level IR) and then MIR (Mid Level IR) before finally generating machine code via LLVM. 

Other desugaring takes place at the HIR stage detailed [here](https://rustc-dev-guide.rust-lang.org/ast-lowering.html).
